☕ Java Depth Questions

Concurrency & Memory Model

Java Memory Model — happens-before
Hard
"Explain the Java Memory Model. What does happens-before guarantee and why does it matter for shared state?"
Show answer
The JMM defines visibility rules between threads. happens-before is a partial ordering: if action A happens-before B, B is guaranteed to see A's writes.

Key edges: volatile write → volatile read (same variable), monitor unlock → lock (same monitor), Thread.start() → first action in started thread, and thread termination → Thread.join() return.

Without it, the JIT and CPU caches can reorder writes. Classic bug: double-checked locking without volatile — the reference can be visible before the constructor completes.

In PADO — model-state updates shared across drift-detection threads used volatile flags and AtomicReference to avoid stale cache reads triggering unnecessary redeploys.
ExecutorService vs Virtual Threads (Java 21)
Medium
"When would you use a thread pool versus Java 21 virtual threads? What are the trade-offs?"
Show answer
Thread pools (fixed / cached ExecutorService): bounded concurrency, good for CPU-bound or connection-limited work. You control parallelism and avoid thread explosion. Risk: blocking calls inside a fixed pool starve other tasks.

Virtual threads (Java 21 Loom): extremely lightweight (~1 KB stack vs ~1 MB). Ideal for I/O-bound work — blocking a virtual thread parks it without tying up a platform thread. Write blocking code, get async throughput.

Trade-offs: Virtual threads don't help CPU-bound tasks (still 1 CPU core per runnable). Pinning occurs when native code or synchronized blocks pin the carrier thread — avoid synchronized in hot paths, use ReentrantLock.

My context: PADO's Kubernetes scheduling API calls (blocking HTTP to Kubeflow) are a perfect virtual-thread candidate — we could drop our fixed thread pool and improve throughput without changing business logic.
ConcurrentHashMap internals
Medium
"How does ConcurrentHashMap achieve thread safety without locking the whole map?"
Show answer
Java 8+: uses an array of Node buckets. Reads are lock-free — bucket heads are volatile, so any completed write is immediately visible. Writes lock only the first node of the target bucket (CAS + synchronized on head), so different buckets can be written concurrently.

Treeification kicks in when a bucket has ≥ 8 entries (converted to a red-black tree). size() uses a distributed LongAdder approach (summing per-stripe counters) to avoid contention.

When NOT to use it: putIfAbsent + compute logic that must be atomic requires compute() / merge() — naive read-then-write is a race even with CHM.

Spring Boot & Framework Internals

Spring Bean lifecycle & circular dependencies
Medium
"Walk me through the Spring bean lifecycle. How does Spring resolve circular dependencies?"
Show answer
Lifecycle: Instantiation → Populate properties (DI) → BeanNameAware / BeanFactoryAware callbacks → @PostConstruct / InitializingBean.afterPropertiesSet() → Bean ready → @PreDestroy / DisposableBean.destroy().

Circular dependency (singleton scope, setter/field injection): Spring uses a three-level cache. Level 1: fully initialized beans. Level 2: early references (proxies). Level 3: ObjectFactory for early exposure. When A needs B and B needs A, A is placed in level-3 while B is being created; B gets A's early reference from level-3, then A completes and moves to level-1.

Constructor injection with circular deps → BeanCurrentlyInCreationException (no early exposure possible). Solution: break the cycle — introduce a third bean, use @Lazy, or redesign.

Spring Boot 2.6+ fails fast on circular deps by default — a good thing.
GoF patterns in practice
Medium
"Give me two GoF design patterns you used in production and why you chose them over alternatives."
Show answer
1. Strategy Pattern — PADO model deployment
Different AI frameworks (PyTorch, TensorFlow, ONNX) needed different deployment scripts. I defined a DeploymentStrategy interface with a deploy(ModelConfig) method, and each framework had its own implementation. The calling code was framework-agnostic. Alternative was a giant if-else chain — Strategy eliminated the open/closed violation and made adding new frameworks a one-class change.

2. Observer Pattern — Kafka consumers for model drift
Drift detection emits an event; multiple downstream services (alert, redeploy trigger, metrics exporter) react independently. Rather than the detector knowing all consumers, it publishes to a Kafka topic and each service subscribes. This is the distributed equivalent of Observer — loose coupling, each consumer can fail without affecting others.

Tip: connect patterns to production decisions, not textbook definitions.
Writing testable Spring services
Easy
"How do you write a Spring Boot service that is easy to unit-test? What mistakes make testing hard?"
Show answer
Constructor injection over field injection — lets tests pass mocks without Spring context.
Depend on interfaces, not concrete classes — swap with Mockito or a test double.
Keep services thin — business logic in POJOs/domain objects, not in @Service directly. Domain objects are pure Java, trivially testable.
Avoid static calls and new inside services — they create hidden dependencies.
Use @SpringBootTest sparingly — start the full context only for integration tests. For unit tests use plain JUnit + Mockito.

Common mistakes: auto-wiring a concrete EmailService inside an OrderService — now every OrderService test needs an email server. Interface + mock = instant fix.

Database & Query Optimization

SQL index design for high-scale reads
Hard
"You have a table with 500M rows: orders(id, user_id, status, created_at, amount). Queries filter by user_id + status + date range. How do you design the index?"
Show answer
Composite index: (user_id, status, created_at)

Reasoning — MySQL uses the leftmost prefix rule. A query WHERE user_id = ? AND status = ? AND created_at BETWEEN ? AND ? uses all three columns. Putting user_id first gives the highest cardinality at the leftmost position, narrowing rows fast.

Index ordering matters: equality columns first (user_id, status), range column last (created_at). Putting the range column in the middle would make MySQL stop using the index for status filtering after the range.

Covering index: add amount to avoid a table lookup — (user_id, status, created_at, amount). If the query only selects these columns, MySQL reads the index only (index-only scan).

Partitioning: for 500M rows, range-partition by created_at (monthly/yearly) so old partitions are pruned before index lookup.

Monitor: EXPLAIN ANALYZE, watch for "Using filesort" or "Using temporary" — signals the optimizer gave up on the index.
MongoDB schema: embed vs reference
Medium
"When do you embed documents vs use references in MongoDB? Give a concrete example from your experience."
Show answer
Embed when: data is accessed together, bounded size, one-to-few relationship. Example: a user document embedding their last-3 addresses — always read together, small, no independent lifecycle.

Reference when: data is large/unbounded, accessed independently, or shared across documents. Example: in PADO, model metadata docs referenced training-run docs (a model can have thousands of runs). Embedding would bloat the model doc and make listing models slow.

Practical rule: start embedded, normalize when documents exceed ~16 KB or when the embedded array grows without bound.

Anti-pattern: unbounded arrays inside a document (e.g., appending every event to an array). MongoDB document max is 16 MB — this becomes a time bomb at scale. Use a separate collection with a reference.

🏗 System Design Questions

Apple design rounds expect you to call out failure modes, not just the happy path. Always discuss: what breaks at 10x traffic, how you detect it, how you recover.
Design a high-scale notification service (Apple-style)
Hard
"Design a notification service that sends push notifications to 500M Apple devices globally with sub-second delivery and at-least-once guarantee."
Show answer
Core flow: Producer → Kafka topic (partitioned by user_region) → Notification Worker Pool → APNs Gateway → Device

Kafka design: partition by device_token_hash for ordering per device. Use idempotent producers + acks=all for durability. Retention = 24h (notifications older than 24h are stale).

Worker pool: stateless Spring Boot microservices on Kubernetes, auto-scaled via KEDA based on consumer lag. Each worker batches APNs HTTP/2 requests (APNs supports multiplexing — 500 streams per connection).

At-least-once: commit Kafka offset only after APNs returns success or permanent failure (token invalid = discard). On transient APNs error → don't commit → message retried. Deduplication at device via notification_id (APNs collapses duplicate push IDs).

Rate limiting: APNs has per-bundle-ID quotas. Use Redis sliding window counter per bundle_id. Back-pressure: if limit hit, pause consumer and retry after window resets.

Global: deploy worker pools per region (US/EU/APAC). Kafka MirrorMaker 2 replicates across regions. Devices are routed to nearest APNs endpoint — lower latency, regional blast radius.

Observability: Kafka consumer lag (alert > 10k), APNs error rate, end-to-end notification latency (p99), dead-letter queue size.
Design a rate limiter for Apple's API gateway
Hard
"Design a distributed rate limiter that limits API calls per user across multiple data centers with minimal latency overhead."
Show answer
Algorithm choice: Token Bucket — smooth burst handling, Redis-native with INCRBY + TTL. Sliding Window Log is accurate but memory-heavy at Apple scale; Fixed Window is fast but allows 2x burst at window boundary.

Redis implementation (token bucket via Lua script — atomic):
local current = redis.call('GET', key)
if current == false then
  redis.call('SET', key, capacity - 1, 'EX', window)
  return 1
elseif tonumber(current) > 0 then
  redis.call('DECR', key)
  return 1
else
  return 0
end
Lua runs atomically on Redis — no race conditions.

Multi-DC challenge: strong consistency across DCs adds latency. Preferred approach: local Redis + async sync. Each DC has its own Redis and tracks a local counter. Background job syncs global usage every 100ms. Allows slight over-counting (10% tolerance) in exchange for sub-millisecond local checks. Hard limits use synchronous global Redis (Redlock) only for the last 5% of quota.

Fallback: if Redis is unavailable, fail open (allow requests) with an alert — never block all traffic because the rate limiter is down.
Your PADO design walk-through
Medium
"Tell me about the most complex distributed system you've designed or contributed to."
Show answer
Use PADO as your anchor story. Structure:

Context: Samsung's internal AI platform serving ML model lifecycle — training, deployment, monitoring, auto-redeploy — across multiple Kubernetes clusters globally.

Problem: Model drift in production causes silent accuracy degradation. We needed a system that detects drift and auto-redeploys without human intervention. Scale: hundreds of models, thousands of inference calls/min.

My design: Monitoring service publishes drift events to Kafka topic. Drift consumer evaluates severity (threshold config per model). On trigger → calls Kubeflow pipeline to retrain on fresh data → deploys new version with blue-green switch → old version torn down after health checks pass.

Challenges: (1) "Build once, deploy to many clusters" — each cluster has different resource constraints. Solved with a cluster-descriptor config and Kubernetes Operator pattern. (2) PV (persistent volume) mounting for training data across clusters — required cluster-specific storage class mapping.

Tech lead role: I owned the architecture, assigned the Kafka consumer and Kubeflow integration to two engineers, personally built the Keycloak SSO layer (most security-critical), reviewed all PRs, and presented the design to Samsung's AI team leads.
