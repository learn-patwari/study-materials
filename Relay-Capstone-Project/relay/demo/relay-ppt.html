The Problem

Building reliable AI workflows is hard

💥

Process crashes lose state

A worker dies mid-step and the run restarts from scratch — or vanishes entirely.

🔁

Side effects fire twice

Retry logic causes double charges, duplicate emails, and duplicate API calls.

🤖

AI output is unconstrained

LLMs return anything. Downstream code breaks when the shape changes unexpectedly.

🔒

No human oversight

Sensitive operations execute automatically. There is no point to pause and require approval.

03 / 10
Solution

What Relay does

01

Versioned workflow graphs

Define multi-step workflows as JSON graphs. Publish a version to freeze it — running workflows never change mid-execution.

02

Durable execution

State lives in PostgreSQL. A crash mid-node rolls back cleanly. The worker resumes from the exact same node on restart.

03

Exactly-once side effects

An idempotency ledger with a unique key per (run, node, attempt) ensures each side effect fires exactly once — through crashes.

04

Schema-validated AI output

AI nodes validate LLM output against a JSON Schema before any downstream node sees the result.

Engine

Six node types

condition

Branch

Evaluates a Mustache expression against run input. Routes to onTrue or onFalse.

http_request

HTTP Call

Calls an external API. Mark sensitive: true to require approval before execution.

ai

AI Node

Calls an LLM, validates output against a JSON Schema. Fails deterministically on invalid output.

approval

Gate

Pauses the run. Resumes on GRANTED; moves to REJECTED status on denial.

delay

Delay

Parks the run for a configurable duration before proceeding to the next node.

notify

Notify

Sends a message to a channel using a Mustache template resolved against run context.

06 / 10
AI Node

Schema-validated LLM output

Every AI node declares an outputSchema. The engine validates the LLM response against it before passing the result to any downstream node.

If the LLM returns anything that doesn't match — wrong type, missing field, invalid enum — the run fails immediately as non-retryable. The AI produces data, never authority.

Claude APIProduction — Anthropic claude-opus-5
OllamaLocal — any OpenAI-compatible endpoint
MockDev / CI — deterministic, schema-aware
"classify": { "type": "ai", "config": { "prompt": "Classify: {{input.ticket}}", "outputSchema": { "type": "object", "required": ["category"], "properties": { "category": { "type": "string", "enum": [ "bug", "feature", "question" ] } } } } }

Approval Gates

Human oversight, built into the engine

Mark any node sensitive: true and Relay hard-blocks it before execution. The engine never delegates this check to the AI.

A pending approval is created and the run parks. A human approves or rejects via the console or REST API. On approval the run resumes from the exact node it was waiting at — even days later.

Correctness Guarantee

Exactly-once side effects

What if the worker crashes after calling the charge API but before recording that it did? Without protection, the retry would charge the customer twice.

Relay prevents this with an idempotency ledger — a side_effects table with a unique key per (run, node, attempt). The first worker wins the insert and performs the effect. Any retry finds the existing row and replays the stored result.

Worker 1 — calls charge API, stores result wins
Worker 2 — finds existing row, replays result replay
charge fired exactly once ✓
-- unique constraint enforces exactly-once CREATE TABLE side_effects ( run_id UUID NOT NULL, node_id TEXT NOT NULL, attempt_key TEXT NOT NULL, result JSONB, UNIQUE (run_id, node_id, attempt_key) ); -- insert-or-skip pattern INSERT INTO side_effects (run_id, node_id, attempt_key, result) VALUES ($1, $2, $3, $4) ON CONFLICT DO NOTHING;

Summary

What Relay delivers

Durable

State survives process crashes. Resumes from the exact failed node.

Exactly-once

Idempotency ledger prevents double side effects across retries and crashes.

Human-in-loop

Sensitive nodes pause for approval. Rejected runs never fire the side effect.

AI-safe

JSON Schema validation ensures the engine, not the LLM, controls what flows downstream.

Built on Java 21 · Spring Boot 3 · PostgreSQL with a DB-backed transactional outbox — swappable for Kafka without changing the execution model.
